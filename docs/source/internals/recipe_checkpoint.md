# Recipe Graphs and Checkpoint Migration

Recipes are declarative graphs. Runtime datasets are wrapper trees. Checkpoint migration connects the two
by matching stable leaf identities while retaining as much compatible progress as possible.

## Recipe graph construction

The main graph nodes are:

- `DatasetReference`, a leaf path plus split, subset, shuffle, filter, and tag settings;
- `RecipeBlend` and `RecipeBlendEpochized`, weighted child graphs;
- `Subset`, which expresses relative or absolute selection;
- `Recipe`, which owns named splits and resolves the full graph.

`Recipe.post_initialize` resolves references relative to the recipe root and validates the resulting graph.
`get_datasets` builds runtime factories. `traverse` visits the same logical leaves without constructing the
runtime pipeline; use it for preparation, diagnostics, and graph inspection.

## Nested option composition

When a reference wraps another recipe or reference, its settings compose with the inner settings:

- positive shuffle-over-epochs multipliers multiply;
- a shuffle value of `-1` dominates positive multipliers;
- `None` disables the composed shuffle and therefore dominates all numeric values;
- relative subsets compose through the nesting;
- absolute subset bounds belong at the concrete leaf, where the absolute sample space is known;
- inner tags are retained, with outer values overriding the same keys;
- an outer split selection may choose a different split of a nested recipe.

Keep these rules in one graph-resolution layer. Applying a subset a second time in the reader or moving
shuffle composition into a wrapper changes leaf identity or iteration order.

## Leaf identity

Checkpoint migration derives a `ResumeIdentity` from recursively serializable dataset configuration. Its
significant fields are:

- normalized dataset path;
- selected split part;
- typed subset;
- filter name;
- auxiliary identity data.

The metadata walker recursively inspects wrapper children. Within configuration values it finds leaf
descriptions containing `_path`, including nested descriptions rather than only the root config object.
Typed subsets are hashable so identities can be compared as sets and preserve the difference between
relative and absolute selection.

A leaf factory should expose stable identity information through `config()`. Renaming or removing identity
fields is a checkpoint-migration change even when exact restoration of an unchanged runtime tree still
works.

## Migration algorithm

Migration starts from a clean state generated by the current dataset topology. It then overlays compatible
saved progress:

1. If type, configuration, and child structure are identical, saved state can be reused deeply.
2. A leaf with the same type and identity set can reuse its saved state; otherwise it stays fresh.
3. A non-blend wrapper with the same type and child count can match children positionally.
4. Otherwise, a current child first looks for an identical saved identity set.
5. If no exact match exists, a unique best identity overlap may be used.
6. Ambiguous or unmatched children retain their fresh state.

`BlendDataset` deliberately does not use positional child matching. This allows recipes to add or reorder
blend children without assigning one dataset's progress to another.

Migration preserves loader-level worker state that is independent of the changed dataset tree, including
worker random state, sample-index scopes, offsets, worker scheduling, and the current micro-batch. The
dataset subtree comes from the migrated current topology.

Some wrappers need a deliberately fresh local state even when children migrate. For example,
`GroupBatchDataset` resets group and batch indexes and pending buckets because those buffers cannot be
safely reinterpreted under an altered graph.

## Exact restore is stricter

Migration is not a promise that arbitrary recipe edits reproduce an uninterrupted run bit for bit.

- **Exact restore** requires the same compatible runtime tree and continues the exact stream.
- **Migration** preserves confidently matched leaf progress and initializes changed structure safely.

Adding a blend child, changing a filter, or changing a subset can therefore be accepted by migration while
producing a different future stream. User-facing behavior and examples are documented in
[Saving and Restoring](../basic/save_restore.md).

## Developing graph changes

When adding or changing a recipe node:

1. define how it resolves nested paths, splits, subsets, shuffle values, and tags;
2. ensure `traverse` and runtime construction find the same leaves;
3. ensure the resulting leaf factory config contains stable identity fields;
4. decide whether child order is semantic;
5. decide which wrapper-local state can migrate and which must reset;
6. test unchanged exact restore separately from changed-topology migration;
7. classify any identity, state-layout, or order change using {ref}`compatibility`.

At minimum, migration tests should cover:

- unchanged graph round trips;
- addition and removal of a blend child;
- blend reordering;
- nested recipes and split overrides;
- relative and absolute typed subsets;
- filters and multiple leaves sharing a path;
- ambiguous identity overlap, which must fail safe by using fresh state;
- buffered wrappers whose own pending state is intentionally reset.

The core tests are in `test_checkpoint_resume.py` and the recipe save/restore tests in `test_recipe.py`.
